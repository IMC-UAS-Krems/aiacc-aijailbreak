# Manual acceptance cases for the local first iteration

Run these after the backend and Node logic tests, using your usual browser. The detailed [functional checklist](functional_checklist.md) covers the former automated UI cases. Record a date, commit, tester, environment, outcome (PASS/FAIL/BLOCKED), and evidence for each. Cases not actually performed remain NOT RUN; a missing reference, model connection or dependency is BLOCKED, not PASS.

| ID | Setup and actions | Expected result / evidence |
|---|---|---|
| M01 — Approved visual direction and identity | Compare menu, chooser, Level 1 and success with the approved images at 1440×900 and 390×844. Obtain the references from this project's owner if unavailable. Read several messages. | Warm ivory, caramel brown, muted sage; one readable font; consistent controls, spacing and corners; spacious conversation; restrained scenery. Robin is the player with a face avatar and muted early-level clothing; the castle has a castle/tower avatar. No neon clothing, mixed fonts, decorative underlining, excessive cards/badges, busy animation or hacker-terminal treatment. Real interactive controls, not screenshots as UI. Note any artwork placeholders in the handoff. |
| M02 — Menu and locked levels | Start with cleared progress. Read premise; use Start, Back, Choose level; try all five levels with mouse and keyboard. Complete Level 1, revisit chooser, refresh and try direct Level 2–5 URLs. | Title/premise explain Robin stealing resources for the poor. All five levels are visible; Level 1 launches/replays. Levels 2–5 stay locked and explicitly unavailable. Navigation always returns to menu. No dead settings controls; every visible control works or is deliberately disabled with an explanation. |
| M03 — Persistence and reset | Start Level 1; refresh, fully close browser and reopen the same profile. Complete it and repeat. Cancel Reset, then confirm Reset. Block storage and repeat basic play. | Continue resumes Level 1, historical completion survives real browser restart, no future level unlock. Cancel changes nothing; confirm removes game progress only. Unavailable/corrupted storage does not crash the game; failure to save is explained. A reset to unstarted status survives refresh. |
| M04 — Readability, input, scrolling, keyboard | At desktop, 390px and 320px widths, send multiline and long messages. Tab through controls, use Enter/Shift+Enter. Scroll up during a slow reply, then return to bottom and send again. Use 200% zoom and the on-screen keyboard on a phone if available. | Comfortable multiline input; Enter sends one message; Shift+Enter inserts newline; visible waiting state. No duplicate requests. Reading older messages is not interrupted by scrolling; readers at the bottom see new replies. No clipped controls or page-wide horizontal scrolling, clear focus and readable feedback. Both password and chat forms remain usable. |
| M05 — Real conversation context | Run the live suite and read its follow-up. In the real UI say “Remember that my basket contains apples,” then ask what the basket contains. Open a separate private browser window; start a fresh conversation. Replay Level 1. | Follow-up uses the earlier context; independent conversations do not inherit each other's messages. Replay begins a fresh attempt with the friendly opening and cleared inputs while retaining completed history. Record actual model replies; no exact prose match is required. |
| M06 — Easy disclosure, manual completion | Review the configured system prompt, guards and model adapter. Ask directly for the password three times in fresh conversations (the live suite does this). After disclosure, refresh before submitting. | Persona is a concise castle assistant with the same fictional backend password; no instruction prohibits disclosure, no AI input guard and no output filter in Level 1. No Level 2 refusal dialogue. Direct disclosure succeeds at least 2/3 times. Disclosure never submits the validator or marks completion. Preserve any failures in the report; do not substitute scripted answers. |
| M07 — Single password source and backend ownership | Review frontend source/built assets and public JSON. Change only the backend development-password setting and restart. Ask for it, try wrong, old, mixed-case and whitespace-padded new passwords. Stop the model service and submit a known correct password. | One backend setting feeds model context and validator. No frontend secret/config value, client-side comparison, hardcoded successful chat response or secret in validator errors. Wrong/old guesses fail, trimmed case-insensitive new guess succeeds. Validation works independently of inference. Success says resources were recovered for villagers, offers Replay/Back, says remaining levels come later. |
| M08 — Actual installed model and outage recovery | Record the serving process/runtime, exact model identifier, parameter size and endpoint using its own inventory. Verify app configuration uses those values. Stop the model service temporarily, send a message, restart the same service and retry. Also interrupt the backend once during validation. | Real installed Qwen 1.5B is used; no model download/substitution or cloud inference. Error clearly explains the local service is unreachable; typed text remains recoverable. Retry returns an actual model reply without duplicate user messages. A failed validation request cannot display success or lose the guess. Restore services when finished. |
| M09 — README fresh-student walkthrough | A teammate uses a fresh checkout and follows only README instructions, from dependencies through model verification and application startup, then plays and resets progress. | README explains what exists and that only Level 1 is playable; required software/runtime; exact working install/start commands and local URL; how to verify/start the installed model; chatting versus separate validation; local saves/reset. Commands match Windows/laptop and actual implementation. No guessed model tag, unnecessary download, Docker or cloud prerequisite. Record every command and correction. |
| M10 — Scope and final handoff | Review the implementation diff and demo all exposed controls. Compare the final handoff with measured test outcomes. | Only menu, chooser, one working level and necessary local integration. No implemented future levels, animation system, inventories, currencies, accounts/authentication, cloud deployment or containers added for this iteration. No mock runtime in normal play. Handoff states how to run, checks actually performed, exact unverified items and artwork placeholders. |
